# Mayorly app: instructions for Claude

This is the application layer of Mayorly, a life OS: entries filed into ledgers, one desk timer, tomatoes that pay a coin each. Windows and macOS, Electron, React. The product rules come from `mayorly-design`; this repo turns them into code and puts a transparent HUD on top.

## Rules that are not negotiable

- **Every rule lives in `src/core`, and `src/core` stays pure.** No Electron, no DOM, no `Date.now()`, no `Math.random()`. Time, ids and randomness arrive through `Ctx`. If a rule needs the clock, pass it in.
- **State changes only through `reduce()`.** The main process is the only writer. Renderers dispatch actions and render snapshots. Do not add renderer-side state that matters after a restart.
- **The economy is the spec's.** One coin per tomato; a tomato grown on an entry is paid when that entry is cleared (the harvest), ledger time with no entry pays as it goes, a deleted entry forfeits its tomatoes. No bonus for long sittings, coins only from desk time; a completed leisure block costs one coin, rests are free, a block left early is free, nothing is earned on the couch. No streaks, no decay, no penalties, nothing that punishes a hold or a bad week. A ledger with `pays` off (paid work) is outside the economy: its tomatoes ripen and count, mint nothing and are never charged (`ledgerPays` in the reducer). Change `src/core/rules.ts` only after the design repo changes.
- **No AI-generated art.** The app icon is the founder's hand-drawn tomato at integer scale. UI icons come from Phosphor; do not hand-draw SVG icons. A ledger's glyph is a Phosphor name from the catalogue in `lib/glyphs.tsx`; the clerk may *choose* a name from that list (`pickGlyph`), never draw one.
- **No em dashes in user-visible copy.** HUD copy is short, plain, and neutral. The clerk speaks in machine-log voice only.

## Checking your work

```
npm test             core rules
npm run typecheck    everything
npm run web          the HUD at localhost:5199 (?demo for sample data, ?fresh for first run)
npm run ship:mac     build Mayorly.app, install it in /Applications, relaunch it
npm run dist:win     on Windows: build the installer and the portable exe into dist/
```

There is no staging: the founder runs the installed app, so a change is done when the new app is up. On a Mac that is `ship:mac`. On Windows it is `npm run dist:win`, then quit the running Mayorly from the tray and run `dist\Mayorly-Setup-<version>.exe`, which replaces the installed copy and relaunches it. From a Claude desktop session, run the installer with `/S` and start the app with `explorer.exe "%LOCALAPPDATA%\Programs\Mayorly\Mayorly.exe"`, never directly: Claude is a packaged Windows app, so anything it starts directly gets a private copy of `%APPDATA%` (`%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming`), with a different save and sign-in from the Mayorly the founder opens. Those shells also read that private copy, so files there can hide the real ones. `npm run dev` is for iterating (hot reload, and on a Mac with `MAYORLY_DEBUG=1` the `SIGUSR1`/`SIGUSR2` previews, which Windows has no signals for); the dev instance and the installed app share one single-instance lock, so only one runs at a time and the ship script quits whichever is up.

Work through tickets one at a time. For each fix, check it, commit and push it, ship it (`ship:mac`, or `dist:win` and the installer), and verify the installed app is running before closing the ticket or starting the next one. The founder actively tests the installed app.

One codebase, two desktops. `main` is the branch both are built from; the Windows installer and the Mac disk image come out of the same tag (`.github/workflows/dist.yml`). Platform differences live behind `process.platform === 'darwin'` in the main process and `IS_MAC` in the renderer, nowhere else. The portable Windows exe never checks for updates and never registers `mayorly://`, since it unpacks to a fresh temp folder each run.

To screenshot the browser preview at full resolution:

```
SHOT_URL="http://localhost:5199/?demo" SHOT_OUT=shot.png SHOT_JS='...' npx electron scripts/shot.cjs
```

`?demo` and `?fresh` put `window.__mayorly = { dispatch, state }` on the page, so `SHOT_JS` (or the console) can drive the HUD: dispatch a harvest, open the deck with a synthetic keydown, and so on. Parameters go in the environment, which works the same on both platforms; Electron on Windows exits before running the script when a file path is passed as a positional argument. The capture window is offscreen with throttling off; a plain hidden window never runs `requestAnimationFrame`, so Motion animations would stay at their initial frame.

## Things that look like bugs and are not

- **Option+R skips only the current rest.** The configurable global `hotkeys.skipRest` dispatches `desk/skipRest`, which returns to the task saved behind the rest and starts it immediately, including when the rest is held or waiting. It keeps the sitting and swap history, and does nothing outside rest. A superset returns to the same slot rather than advancing; normal Skip still advances the plan.

- **Nothing cleared or deleted is gone.** A cleared entry stays in `entries` with `doneAt` and a `history` of every clear and reopen (`core/history.ts`, with the notes and checklist as they were at each clear). A deleted entry moves to `state.trash` with `deletedAt` (`entry/delete`), keeps its segments and so its tomatoes, and comes back with `entry/restore` (its ledger if it still exists, else the tray; `restoredAt` set). `trash/drop` and `trash/empty` are for good; anything older than `TRASH_KEEP_MS` (thirty days) is purged on the next delete or restore. In a merge the trash is a log where the later deletion wins, and a live entry restored after that deletion stays live (`restoredAt` also counts as a making, so a restore since the last sync is kept). `deck/EntryHistory.tsx` is the screen: cleared or the trash, j and k, Enter, u, x, t, /, Backspace.
- **Task tomatoes come from task intervals.** `accounting.ts` sums each focus segment's end minus start, divided by its sitting's locked tomato length. Fractions survive switches and sittings. `Entry.tomatoes` is a derived cache of whole tomatoes not yet paid; the displayed count includes all work. Mint before switching, parking or clearing. Migration and merge rebuild caches from closed segments, preserve coin records, and never replay historical ledger payments. Entry-free time has a separate counter per ledger in each sitting.

- **Work and rest alarms are per machine.** `settings.alarms` is in `DEVICE_SETTINGS`; each choice has a built-in tone or a local custom asset id. `src/main/alarms.ts` copies uploads into `alarms/` beside the save. Audio bytes never enter state or sync. The renderer decodes a picked file before saving it, caches decoded audio for playback, and plays at most 15 seconds. Preview works with Sound cues off; automatic alarms obey it. The native picker uses `dialogOpen` so the deck stays open.

- **The resting HUD is only the tomato and a number, on both desktops.** Hover gives one line of text and a hop, nothing more. The objectives strip, the centre callouts and the kill feed of the first HUD stay mounted but hidden, everywhere, because the callout plays the block and swap sounds. A hotkey that failed to register speaks through the pet's caption, not a toast. Hold, skip, clear and stand down live in the Plus menu and the command line; there is no control strip.
- **The overlay window is never focusable in field mode.** That is how it avoids stealing keystrokes. Plus, deck and capture flip it on and hand focus back with `blur()`.
- **A held Alt+T fires the command repeatedly.** The renderer ignores repeats until the key is released; releasing after 400 ms closes the menu (hold to peek), unless an arm was steered meanwhile, which commits the open.
- **The Plus menu's keys are the keymap's `plus` scope**, matched by position with Option ignored (`actionFor(e, 'plus', settings, { ignoreShift: true, ignoreAlt: true })`), so they work while the swap key is still held. Digits 1 to 9 pick the item at that number in the arm you are on; every tile shows its number. `useFit` remeasures on resize, through a ResizeObserver and on timers after mount, because the menu mounts while the window is still pet-sized.
- **Alt+arrow and Alt+digit while the Plus menu is open are global shortcuts.** The swap key's modifiers plus Up, Down, Left, Right or 0 to 9 are registered as the menu opens and released as it closes, so Alt+T and Alt+Left (or Alt+1) in the same breath land before the window has the keyboard. They arrive as `arm-*` and `pick-*` commands; `plus/arms.ts` is the one path that points at an arm or a number, and a point made before the menu mounts waits as a hint. In the menu, 0 is always the couch: a tile at the end of the ledger arm that turns the entry arm into the couch list.
- **A swap does not reset the block clock** except in blitz, where the timer belongs to the entry. A swap you ask for (the Plus menu, Alt+Q) also resumes a desk on hold or waiting, so switching tasks is one act; a swap the desk makes on its own, such as the next entry after a clear, leaves a hold alone.
- **The Plus menu previews choices until it closes.** Ledger, entry, mode and couch picks stay in temporary UI state. `App` sends the final `desk/select` once on every exit path, and the reducer applies it against the current desk. Browsing never changes swap history or resumes a held timer; opening and closing without a pick does nothing. Orders close the menu before taking effect.
- **Superset slots with nothing open still run**, as ledger time.
- **Deploying a different task parks the running session.** The desk holds one parked session in `desk.holster`, with its own sitting and the time already spent on its block. Picking the current task keeps its clock; picking a parked task resumes that session. `desk/switch` (Alt+Q) swaps the two; a stand down brings the parked one back paused. Nothing is minted while parked.
- **A rest is never a quick-switch target.** Before advancing into rest, `advanceDesk` saves its task and plan position in `desk.restTask`. Parking or switching resolves the rest to that task with a fresh block, keeping the completed focus count and the next leisure charge id. During rest, swap-back still prefers the previous real task. Old saves resolve a parked rest from the sitting's segments. Automatic rest cadence is unchanged.
- **Alt+Q is a two-place toggle, and a swap-back beats the parked session.** Every swap writes the entry it left into `desk.previous`; the switch swaps back to it inside the same sitting, like a primary and a secondary weapon, and only falls back to the holster when there is no such entry. A swap to a third entry drops the oldest, parked or not; a cleared entry on the other side gives way to its ledger. The parked session still returns on a stand down.
- **A desk found running at launch is paused at the last heartbeat.** Time the app could not see is not desk time.
- **`npm run web` with no query loads from localStorage**; `?demo` and `?fresh` never write to it.
- **The clerk cannot touch a user event, by type.** `ClerkCommand` has no op that names an event id; `place` and `block` make `clerk` events, refused when they overlap a user event or outside busy time, and `unplace` removes only `clerk` pins. The model names entries by title; `arrange.ts` resolves titles to ids (exact, prefix, substring, token overlap with a margin, else a pick), converts its wall-clock times in the calendar's zone, drops the past, previews with `reduce` and holds the proposal five minutes; `schedule/apply` checks every command again against the live state.
- **Every open entry is planned, estimate or not.** `replanned()` places an entry without an estimate at `settings.calendar.defaultMin` and marks its blocks `assumed`; `horizonDays` is the range (1, 2, 7 or 14 in Settings; any 1 to 28 is kept) and the plan ends at the end of its last day (`horizonEndFor` in `shared/windows.ts`, the one place); `mode` is `done` (by due, then the flow) or `rotate` (`order()` in `schedule.ts`: rush, then one task per ledger per round). The ask box is for corrections; the plan is made without asking.
- **The calendar's blocks are derived, and a missed block just replans.** `schedule/replan` is computed before the state is cloned and returns the same reference when nothing moved, so the once-a-minute replan costs nothing; blocks are rewritten whole, keyed `entryId#chunk` with a `seq` that bumps when the times move (the feed's UID and SEQUENCE). Nothing is minted or owed for a block; a block nobody started is simply placed again. The user's events (`calendar.events`) are busy to the planner and never moved; a pin (an event with an `entryId`) is also credit toward that entry. Work hours are expanded outside core in `settings.calendar.tz`, which syncs, so two machines plan the same windows.
- **The quick drawer (Alt+Shift+R) is its own window on a Mac.** `overlay.toggleDrawer` hangs a `DRAWER`-sized panel under the pet (over it when the pet sits low) that loads `?drawer` (`DrawerApp` in `hud/Drawer.tsx`); the pet's window never changes, so the tomato never moves. It is focusable, and closes on blur, on Esc from its page (`closeDrawer`), or on the hotkey again. It is kept hidden between uses, so every broadcast from main goes to `overlay.pages()`, the pet's window and the drawer's; a drawer that only heard the state it loaded with showed the entry from an earlier sitting. On Windows and in the browser the overlay draws the same component as the `drawer` mode, in the box the Mac gives that window (`drawerBox` in `src/shared/pet.ts`); only the drawer and the pet take the pointer then, so a click anywhere else reaches the app beneath and the blur closes the drawer, as on a Mac, and nothing dims. Notes and subtasks live on the entry (`entry/note`, `entry/subtask-*`), rules on the leisure item (`leisure/cue-*`), all through the reducer.
- **One geometry for the pet, two ways of drawing it.** `src/shared/pet.ts` says where the pet, its caption and the drawer sit relative to the tomato (the anchor, its bottom centre). The shell turns those boxes into windows on a Mac; on Windows the page draws the same boxes inside the overlay. `pet.test.ts` holds the functions to the Mac window's original formulas, so a change there moves both desktops or neither.
- **On Windows the pet goes anywhere too.** The overlay still covers the work area, but the page draws the pet where the tomato was left (`Layout.pet`, in the overlay's pixels), and the tomato is dragged by the page (`Pet.tsx`, pointer capture, then `placePet`); while it is held the overlay keeps the pointer, even past a clamped edge. A drop past the edge lands on the display there and the overlay follows. Alt+G, the arrows and 1 to 4 move it as on a Mac. The place is `hud.json` beside the save on both desktops. A first run takes its side from `hudSide`; after that wherever the pet is decides `hudSide`, and the Side buttons in Settings snap it to that bottom corner. A display whose work area is the whole screen has an auto-hidden taskbar, so the home spot and the bottom corners keep 48px clear for it to slide into.
- **On a Mac the window is the pet, not the screen.** Field mode is a panel the size of the pet (`PET` in `src/shared/pet.ts`: the sign's column, the tomato, room for two lines of task), movable by dragging the tomato or with Option+G, and it takes clicks like any small window. The hover caption is its own click-through window just above the tomato, and it only says what the pet does not already show. Nothing is click-through on macOS; the `data-hit` path is Windows only. Plus, deck and capture grow the window to the work area and shrink it back. The position is saved in `hud.json` beside the state file.
- **On a Mac the field HUD polls the cursor for hover.** AppKit only sends mouse-moved events to the key window, and the pet never is one, so `overlay.ts` samples the pointer and feeds the page the same mousemove.
- **Two kinds of keys.** `settings.hotkeys` are global Electron accelerators, registered by the shell and kept per machine (`DEVICE_SETTINGS`). `settings.keymap` are in-app keys read by the renderer alone, named like `list.down`, and they sync. A key the user did not change is not in `keymap` at all; `keysFor` falls back to the default in `lib/keymap.ts`.
- **Text size is per area and per machine.** `settings.text` (`pet`, `deck`, `plus`, 0.8 to 1.6, in `DEVICE_SETTINGS`): the pet's task line reads `--text-pet`, the deck body zooms by `--text-deck`, the swap menu multiplies its fit by `text.plus`, and on a Mac `overlay.setTextSize` gives the pet window the height two bigger task lines need (`TASK_LINES`).
- **Hotkeys are stored as `Alt+T` on a Mac too.** Alt is Electron's cross-platform spelling for Option. The HUD labels them Option, the Settings field accepts Option, Cmd and Control and stores Alt.
- **Clicking the menu bar icon on a Mac opens the menu, not the Deck.** That is the macOS convention; Deck is in the menu.
- **The app has an application menu but no menu bar.** An accessory app shows none; the menu exists so Cmd+C, V, X, A and Z work in text fields and Cmd+Q quits. Cmd+W closes the open panel.
- **`backups/` fills up on its own.** One copy a day, one before a sync or an import replaces the state; `Store.load` falls back to them when the save cannot be read. A file dialog of our own sets `dialogOpen`, so the blur that would close the deck is ignored while it is up.
- **`mayorly://` is registered only in a packaged build**, and `open-url` can arrive before boot, so it is queued at module level.
- **Every build carries a stamp.** `build-info.ts` puts the version, the short commit (with a `+` when the tree was dirty), the build time and the top section of `NOTES.md` into every bundle as `__MAYORLY_BUILD__`. The first launch of a build on a machine opens the deck on the What changed card; `notes.json` beside the save remembers the build seen, a first run marks it seen without showing it, and Settings shows the build and brings the card back. Write the top section of `NOTES.md` in plain words before shipping.
- **The updater is silent.** Errors go to the log. A build installed by `ship:mac` has no `app-update.yml`, so it never checks; the portable Windows exe carries one but never checks either (`PORTABLE_EXECUTABLE_DIR`), or it would install the setup on quit; a signed download build without a Developer ID logs one error per check, which is expected until the certificate exists.
- **A deleted account's token still verifies.** `requireAuth` on the server looks the user row up on every request; the missing row is what answers 401.
- **Find or start (`capture/Find.tsx`, Alt+F) is search on top of capture.** `findEntries` ranks the open entries; Enter sends `desk/select`. A line nothing matches goes through the capture box's own `plan`, so ledger prefixes, estimates and `/` orders all work.
- **Capture and start skips the clerk's wait.** `entry/capture` with `start` files by prefix and puts the entry on the desk in the same reduce (a focus block swaps to it and resumes, anything else deploys a pomodoro); `captureLine` then asks the clerk and, if it names another ledger, dispatches `entry/file`, which moves a block that is on that entry along with it.
- **A dragged block is a pin.** The planner owns a block's time; dragging one dispatches `calendar/pin` with the new `start` and `end`, which makes a user event on the entry, and the next replan routes around it. An event drags whole or resizes by its bottom edge (`calendar/event-update`). The pointer is captured by the item and read by the grid; a press that moves less than 4 px is a click, which selects.
- **The AI clerk never writes state itself.** It returns a `Filing`; `entry/capture` and `entry/file` in the reducer check it (real ledger, real title) and file by prefix otherwise. Keys live in `ai.bin`, sealed (`src/main/seal.ts`), never in state; they sync only through the key vault below.
- **AI keys sync end to end, apart from the document.** `ai/keysync.ts` and `ai/vault.ts`: with a sync passphrase set in Settings, each computer seals its keys (scrypt, then AES-256-GCM) and names each with an HMAC of the key, and `/vault/items` on the server upserts by that name. The same key on two computers is one key, distinct keys all stay, and a removal remembered in `ai.bin` beats an add made before it. The passphrase is never stored; the keys made from it are, in `ai.bin`. A key that arrives is checked again on this computer (`checking`), since models and status are per computer; so are the preferred model and provider. Any number of keys per provider: adding another keeps both, and a failing one hands the next call to the next. Sync runs on sign-in, every five minutes, on any key change, and when Settings asks for the AI state. Signing out forgets the passphrase's keys.
- **A correction is a house rule.** Entries the clerk filed carry `clerkFiled`; moving one writes a `HouseRule` in the reducer, in words, naming the ledger chosen and the ledger wanted. Rules are state, sync with the account, and go into every clerk prompt ahead of the criteria.
- **Interfaces close on a click outside and when the window loses focus.** The shell sends `close` on blur; the renderer closes on a pointer down outside the open panel.
- **Sync is last writer wins on the server, and never loses work on the client.** A server document enters this machine through `sync/replace` (taken whole, when nothing changed here since the last sync) or `sync/merge` (unioned with this machine's work otherwise; `src/core/merge.ts`); both keep this machine's own settings (`DEVICE_SETTINGS`), and the desk follows the active device (below). `sync.json` beside the save holds the revision, the time and the hash of the last match. A document the reducer refuses blocks syncing until the app is updated. The server stores JSON, a revision and a per-user token version, and for key sync only blobs it cannot open.
- **One active device per account, and only it runs the desk.** `desk.device` is the computer a person used last and when; every user action claims it first (`engine.act` sends `desk/claim` ahead of the action, in the same step), while ticks, replans, sync, the clerk's filing and the sleep, lock and launch pauses go through `engine.dispatch` and claim nothing. Sync keeps the desk claimed later (`deskWinner` in `merge.ts`). On a tie, on the active device itself, its own desk always wins (`ctx.device` is passed in): the clock advancing claims nothing, so the server's copy with the same claim is only an older push of this desk, and taking it wound a finished rest back to the start. Elsewhere on a tie the active device's own copy beats one another computer holds. A computer that receives a desk running elsewhere holds it where it stands as it arrives (`heldAt`), and runs, mints and rings nothing; the pet says where it is running. Anything a person does there takes it over, and the clock carries on from the hold as if it never stopped, never past the end of the block. The computer that lost it closes its run at the moment of the takeover. The run the kept desk is timing is never overwritten by another copy; otherwise intervals merge with the later end winning. The device id is `device.json` beside the save; the name is the host name. A hold is a view of the owner's run, not a record: its interval end never beats the owner's, focus totals are always re-summed from the intervals (`focusFromLog`), and `syncContent` leaves the held desk out, so holding writes nothing. A push goes only when this computer has something the server lacks; plan-only changes go from the active device, at most every 15 minutes, for the calendar feed.
- **Accounts need `MAIN_VITE_API_URL` and `MAIN_VITE_GOOGLE_CLIENT_ID` at build time** (see `.env.example`). Without them the Settings tab has no Account section and nothing talks to the network.
- **A Mac build is ad-hoc signed, not notarized.** There is no Developer ID. Gatekeeper refuses the first launch and offers Open Anyway in Privacy & Security. `npm run dist:mac` only works on macOS.
- **`ship:mac` signs with the local certificate "Mayorly Local"** when `scripts/local-cert.sh` has put one in the login keychain, so every build has one identity. A Developer ID (`CSC_NAME`) still wins.
- **On a Mac, secrets are sealed with a local key, not the keychain.** `seal.ts`: `session.bin` and `ai.bin` are AES-256-GCM under `seal.key` beside the save (0600). The keychain's Always Allow is tied to a partition list that, for an app without an Apple team identifier, holds a cdhash per build, so safeStorage asked for the login password after every ship, signed or not. A self-signed certificate cannot carry a team identifier. Windows and Linux keep safeStorage (DPAPI, the keyring), which never asks. A file the keychain sealed is opened once more and resealed.
